# CLAUDE.md — unitrack

Точка входа для Claude Code. Здесь собраны только общие правила; подробности — в
специализированных документах `docs/ai/` (см. «Документы»).

## Проект

unitrack — headless-ядро музыкального плеера на плагинах, не зависящее от UI, бэкенда и
платформы. Трек (`LogicalTrack`) — это идентичность с несколькими источниками; ядро выбирает,
какой из них воспроизвести, по настраиваемой политике. Всё конкретное (источники, движки
воспроизведения, метаданные, плейлисты) живёт в плагинах. Монорепо npm workspaces, чистый ESM
JavaScript с типами в JSDoc, без шага сборки JS.

## Перед началом задачи

Прочитай релевантные разделы:
- [`docs/ai/ARCHITECTURE.md`](docs/ai/ARCHITECTURE.md) — какие модули затрагиваются, их границы
  и точки расширения;
- [`docs/ai/DEVELOPMENT.md`](docs/ai/DEVELOPMENT.md) — как вносить изменения, тестировать и
  проверять результат.

## Workflow

**Understand → Plan → Implement → Verify → Report** — что делать на каждом этапе описано в
`DEVELOPMENT.md` §1.

- **Understand** — изучить существующую реализацию, затрагиваемые модули и зависимости.
- **Plan** — для нетривиальных изменений сначала сформировать план.
- **Implement** — изменить только то, что требует задача.
- **Verify** — выполнить релевантные проверки.
- **Report** — сообщить, что изменено и что проверено.

## Ключевые ограничения

- Не менять код вне scope задачи.
- Не делать несвязанные рефакторинги.
- Не нарушать архитектурные границы (`ARCHITECTURE.md` §5).
- Не угадывать при неоднозначных требованиях: сообщить, что обнаружено, какие есть варианты,
  что предлагаешь и почему (`DEVELOPMENT.md` §8).
- Перед изменением существующего кода изучить его usages, зависимости и тесты.
- Сохранять публичные контракты, если изменение явно не требуется.
- Не исправлять расхождения между документацией и кодом без явной задачи — фиксировать их.

## Проверка результата

Выполни релевантные тесты, typecheck и сборку типов — команды, порядок и минимальный набор
описаны в `DEVELOPMENT.md` §5–6. В отчёте укажи, что именно было запущено и с каким результатом,
и что не проверялось (например, ручная проверка Electron/звука) и почему.

## Формат финального ответа

```
Summary:                что сделано и зачем
Changes:                затронутые файлы и суть изменений
Verification:           какие проверки выполнены и их результат
Risks / Open Questions: ограничения, неоднозначности, риски, вопросы
```

Держать компактным для обычной задачи (подробнее — `DEVELOPMENT.md` §9).
