# 1. Краткое описание AI-инструмента

Для выполнения задания был выбран **Claude Code**.

В качестве проекта использовался `unitrack` это мой личный пет-проект, реалиузует безголовый музыкальный плеер на основе плагинов. Это JavaScript monorepo с npm workspaces. Проект построен вокруг плагинной архитектуры: core отвечает за основные абстракции и управление воспроизведением, а конкретные источники данных, playback engines и интеграции реализуются через плагины.

Для специализации Claude Code в проекте был создан основной файл `CLAUDE.md` и набор специализированных документов:

* `CLAUDE.md` — основная точка входа и общие правила работы агента;
* `docs/ai/ARCHITECTURE.md` — архитектура, модули, зависимости и границы ответственности;
* `docs/ai/DEVELOPMENT.md` — правила разработки, кодстайл, тестирование и workflow;
* `docs/ai/TASKS.md` — типовые сценарии задач с примерами промптов и критериями готовности;
* `docs/ai/VERIFICATION.md` — инструкция по самопроверке результата перед завершением задачи.

Такой подход позволяет не перегружать `CLAUDE.md`, а вынести подробные правила в отдельные документы и использовать их как рабочий контекст агента.

# 2. Что было сделано и как проходила проверка инструкций

## Подготовка инструкций

Сначала была описана архитектура проекта: назначение основных пакетов, зоны ответственности, допустимые зависимости и архитектурные границы.

Затем были сформированы правила разработки: требования к изменениям, работе с публичными контрактами, тестированию, форматированию, проверкам и поведению агента при обнаружении неоднозначностей.

Отдельно были описаны три типовых сценария:

1. добавление нового source provider;
2. изменение существующего поведения `CorePlayer`;
3. изменение публичного контракта `ResolvedSource`.

Для каждого сценария были определены ожидаемое поведение AI-агента и критерии готовности результата.

Также была добавлена инструкция `VERIFICATION.md`, которая требует перед завершением задачи проверить diff, соответствие требованиям, архитектурным ограничениям, публичным API, тестам и отсутствие посторонних изменений.

## Практическая проверка

Для проверки инструкций было проведено три теста.

### Тест 1. Анализ изменения публичного контракта

Хотелось проверить, умеет ли агент определить влияние изменения публичного API и остановиться, если для принятия решения недостаточно информации.

В качестве задачи было предложено рассмотреть добавление `expiry` в публичный контракт `ResolvedSource`. Агенту было явно запрещено изменять код.

Результат:

* агент нашёл текущую структуру `ResolvedSource`;
* определил производителей и потребителей контракта;
* проанализировал влияние изменения на source providers, resolver, player и playback engines;
* выявил потенциальную проблему с истечением срока действия URL;
* сформулировал несколько вариантов реализации;
* обнаружил неоднозначности в отношении `CONTRACT_VERSION`, версионирования и поведения core;
* остановился перед внесением изменений и задал уточняющие вопросы;
* файлы проекта не изменялись.

Это соответствует инструкциям: агент не стал самостоятельно принимать архитектурные решения при недостатке информации.

### Тест 2. Анализ изменения поведения `CorePlayer.prev()`

Вторым тестом было изменение поведения метода `prev()`:

* если текущая позиция трека больше 3 секунд — начать текущий трек сначала;
* если позиция меньше или равна 3 секундам — сохранить существующее поведение перехода к предыдущему треку.

На этом этапе также требовалось не изменять код, а сначала проанализировать задачу.

Агент:

* изучил существующую реализацию `CorePlayer`;
* нашёл использование `QueueManager`;
* проверил существующие тесты и связанные сценарии;
* определил способ получения текущей позиции;
* выявил неоднозначности для paused/idle/error состояний, первого элемента очереди и shuffle/repeat;
* предложил минимальный план изменений и необходимые regression tests;
* не стал реализовывать изменение до уточнения спорных моментов.

Это показало, что правила действительно заставляют агента сначала разобраться в существующей архитектуре и требованиях, а не сразу изменять код.

### Тест 3. Реальная реализация изменения

Третий тест был практическим: агенту было разрешено внести изменения в проект после того, как все спорные решения были явно заданы в промпте.

Требовалось реализовать описанное выше поведение `CorePlayer.prev()`.

Дополнительно были заданы конкретные условия:

* порог — строго больше 3 секунд;
* использовать существующий `#position`;
* при restart использовать существующий `seek(0)`;
* не создавать новый playback plan;
* не менять очередь;
* корректно обработать paused state;
* сохранить существующую семантику idle/error;
* добавить regression tests для основных граничных случаев;
* выполнить полный набор проверок проекта.

В результате агент изменил только два файла:

* `packages/core/src/CorePlayer.js`;
* `packages/core/test/CorePlayer.test.js`.

В `CorePlayer` была добавлена логика перезапуска текущего трека, а в тестах — проверки нового поведения и граничных случаев.

До внесения изменений новые тесты ожидаемо не проходили на исходном коде. После реализации:

* `npm test -w @unitrack/core` — 166/166;
* `npm test` — успешно, 345 тестов в 12 test suites;
* `npm run build:types` — успешно;
* `npm run typecheck` — успешно.

Также агент выполнил самопроверку по `VERIFICATION.md`: проверил diff, область изменений, архитектурные границы и тесты.

## Оценка соответствия инструкциям

По результатам проверки видно, что агент следует заданным инструкциям проекта.

В частности:

* сначала анализирует существующую реализацию и зависимости;
* не начинает реализацию при наличии существенных неоднозначностей;
* задаёт уточняющие вопросы вместо самостоятельного принятия архитектурных решений;
* ограничивает область изменений необходимыми файлами;
* учитывает архитектурные границы проекта;
* добавляет regression tests для изменения поведения;
* выполняет предусмотренные проверки;
* в финальном ответе отдельно сообщает изменения, проверки, риски и открытые вопросы.
