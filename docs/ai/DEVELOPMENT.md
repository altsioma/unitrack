# Работа с кодом unitrack — инструкция для AI-агента

Архитектурный контекст, границы модулей и точки расширения — в [`ARCHITECTURE.md`](ARCHITECTURE.md).
Здесь — только *как* выполнять задачи. Если правило ниже ссылается на раздел ARCHITECTURE.md,
архитектурное ограничение берётся оттуда, а не формулируется заново.

## 1. Workflow: Understand → Plan → Implement → Verify → Report

### Understand
- Прочитать код, который будет затронут, и **все точки его использования** (поиск по имени
  функции/метода/события во всех workspace, включая `apps/*` и `test/`).
- Определить затрагиваемые пакеты и их зависимости по `package.json` (`dependencies`/`devDependencies`)
  и импортам. Изменение в `@unitrack/core` или `@unitrack/core/types` затрагивает все плагины,
  `conformance-kit`, `ts-consumer-fixture` и оба хоста.
- Найти релевантную design-спеку в `docs/superpowers/specs/` (по имени пакета или теме) —
  она объясняет, *почему* код устроен так, и перечисляет non-goals.
- Прочитать JSDoc-комментарии в изменяемом файле: в проекте они фиксируют инварианты и
  известные ограничения (например, `CorePlayer.#resolveLookaheadPlan`, `types.js`).

### Plan
- Для нетривиальной задачи (больше одного пакета, изменение контракта, поведения очереди/плана,
  новый пакет) — сначала изложить план: какие файлы меняются, какие тесты добавляются, какие
  проверки будут запущены. Дождаться подтверждения, если решение архитектурное (см. раздел 8).
- В репозитории изменения проходят цикл «спека → план → реализация» (README, «How this repository
  works»). Если задача требует новой функциональности или изменения контракта, а спеки нет —
  сообщить об этом и предложить её подготовить, а не реализовывать молча.
- Тривиальные изменения (опечатка, локальный баг-фикс с тестом) можно выполнять без отдельного плана.

### Implement
- Следовать правилам разделов 2–4.
- Не менять ничего за пределами объёма задачи.

### Verify
- Запустить проверки из раздела 6, минимум — тесты затронутых пакетов и typecheck.
- Если проверку запустить невозможно (нет `node_modules`, нет сети, нужен Electron-бинарник
  или звук) — явно указать это в отчёте, не заявлять «проверено».

### Report
- Отчитаться по формату раздела 9.

## 2. Изменение существующего кода

- **Минимальный scope.** Менять только то, что требует задача. Не переформатировать и не
  переименовывать соседний код.
- **Без несвязанных рефакторингов.** Замеченные проблемы — в Notes отчёта, а не в diff.
- **Публичные контракты сохранять.** Публичное API — экспорты `src/index.js` каждого пакета,
  подпуть `@unitrack/core/types`, публичные методы и события `CorePlayer`, формы типов в
  `types.js`. Изменение формы плагинного контракта — ломающее изменение
  (ARCHITECTURE.md §6, строка «Изменение контракта»), требует явного согласования.
- **Поведение не менять без требования задачи.** Это касается и «очевидных» улучшений:
  в коде много намеренных решений, обоснованных в комментариях (например, `''` вместо
  placeholder-MIME в `source-subsonic`, `'transportCommand'` не подписывается ядром).
- **Перед изменением механизма** найти его текущую реализацию, все вызовы и тесты, которые
  его фиксируют. Если тест противоречит задаче — это сигнал уточнить требование, а не удалить тест.
- **Архитектурные границы** — ARCHITECTURE.md §5. Особо: сериализация публичных команд
  `CorePlayer` через `#enqueue`, приватность `QueueManager`, редактирование `token.token`/`headers`.
- Комментарии, объясняющие *почему*, при изменении кода обновлять, если они перестали быть верными.

## 3. Добавление нового кода

Куда класть и какой контракт реализовывать — ARCHITECTURE.md §3 и §6. Практические шаги:

**Любой новый workspace-пакет**
1. Скопировать `package.json`, `tsconfig.json`, `tsconfig.build.json` ближайшего аналога того же
   уровня (так делают планы в `docs/superpowers/plans/`, например `2026-08-20-source-direct-url.md`).
2. `name: "@unitrack/<name>"`, `"type": "module"`, `engines.node`, `exports` с условиями
   `types` → `./dist/index.d.ts` и `import` → `./src/index.js`; скрипты `test`, `typecheck`, `build:types`.
3. Внутренние зависимости — диапазоном на текущую версию пакета (`"@unitrack/core": "^0.2.0"`);
   `@unitrack/core` и `@unitrack/conformance-kit` у плагинов — в `devDependencies`.
4. Выполнить `npm install` в корне, чтобы обновить `package-lock.json` (в истории это
   отдельный коммит или часть того же изменения).
5. Добавить строку в таблицу пакетов в `README.md`.

**Новый модуль внутри существующего пакета** — отдельный файл в `src/` рядом с `index.js`
(как `source-s3/src/sigv4.js`, `source-subsonic/src/md5.js`) с собственным `test/<module>.test.js`.
Наружу экспортируется только через `src/index.js`, если нужно.

**Новый plugin (любая категория)**
- Фабрика `create<Описание><Категория>(config = {})`, возвращающая обычный объект
  (`createS3SourceProvider`, `createAudioQueuePlaybackEngine`, `createLocalFolderPlaylistProvider`).
- `contractVersion: CONTRACT_VERSION` из `@unitrack/core/types`; `initialize`/`dispose` всегда
  присутствуют (могут быть пустыми и должны быть идемпотентны — хосты вызывают
  `initializePlugins()` повторно).
- Тест `test/conformance.test.js` с соответствующей функцией `assert*Conformance`
  (в `source-s3` и `source-direct-url` вызов встроен в `index.test.js` — оба варианта встречаются).

**Новый source provider** — дополнительно: настраиваемый `id` с дефолтом, `canResolve` по
`ref.pluginId === id`, осмысленный `kind`, обоснованные значения `capabilities`
(комментарий почему, как в существующих провайдерах), сообщения ошибок без токена/учётных данных.
Сетевые тесты — через локальный `test/helpers/testServer.js` (`node:http`, порт 0).

**Новый playback engine** — дополнительно: DOM-зависимости внедряются параметрами фабрики
(`AudioConstructor`, `AudioContextConstructor`) для тестов на стабах; `canPlay()` возвращает
`false` для неподдерживаемого `ResolvedSource.kind`; при работе с URL — через
`acquireWebMediaUrl` из `@unitrack/media-delivery-web` с освобождением лизов. Тесты — на
`test/helpers/domStubs.js` / `fetchStubs.js` (дублируются по пакетам, общей зависимости нет).

**Новый shared package** — только для кода без plugin identity, используемого более чем
одним пакетом; в описании `package.json` указать, кто его потребляет и что он не публичный API,
если это так (как у `media-delivery-web`).

**Host-specific код** — только в `apps/<host>/`. Новый плагин подключается через
`apps/<host>/plugins.js` (импорт фабрики + запись в `PLUGIN_MANIFEST` + реэкспорт), регистрация —
в точке входа хоста. Решения, отнесённые к хосту (ARCHITECTURE.md §5), не переносить в ядро.
В `electron-demo` логирование подробное и безусловное — это зафиксированная конвенция
(`docs/superpowers/specs/2026-08-17-electron-demo-queue-ui-design.md`, раздел «Logging»);
новые действия UI/IPC логировать так же, без значений токенов.

## 4. JavaScript / JSDoc / ESM

Правила выведены из текущего кода; линтера и форматтера в проекте нет.

- **Язык:** чистый JavaScript (ES2022, private fields `#x`, `??`, `?.`). Никаких `.ts`, кроме
  `packages/shared/ts-consumer-fixture`. Никакого шага сборки JS.
- **Модули:** только ESM — `import`/`export`, `"type": "module"`; `require`/`module.exports`
  не используются. Электрон-preload — `.mjs`.
- **Экспорты:** только именованные, `export default` в проекте нет. Публичная поверхность
  пакета — `src/index.js` (+ подпуть `./types` у core).
- **Импорты:** относительные — с расширением (`'./Queue.js'`); между пакетами — по имени пакета
  (`'@unitrack/core/types'`), не относительными путями в чужой пакет. Node built-ins — с префиксом
  `node:` (`'node:fs/promises'`). Тесты импортируют тестируемый код через `'../src/index.js'`.
- **Типы:** JSDoc на каждой функции/методе (`@param`, `@returns`, включая `@returns {void}`),
  `@type` на полях классов, `@typedef` для форм. Типы контракта — через
  `import('@unitrack/core/types').SourceProvider` (внутри core — `import('./types.js')`).
  Приведения — `/** @type {any} */ (expr)`. Код должен проходить `tsc --checkJs --strict`.
- **Форматирование (по факту кода):** 2 пробела, одинарные кавычки (шаблонные строки для
  интерполяции), точки с запятой, завершающие запятые в многострочных литералах.
- **Именование:** пакеты `@unitrack/<категория>-<имя>` (`source-`, `engine-`, `metadata-`,
  `playlist-`); в core файлы классов в PascalCase (`CorePlayer.js`, `PluginRegistry.js`);
  в плагинах точка входа `src/index.js`; фабрики `create…`; id плагинов в kebab-case
  (`'local-fs'`, `'web-audio'`); константы `UPPER_SNAKE_CASE`; классы ошибок
  `…Error extends Error` с явным `this.name`.
- **Комментарии:** подробные, объясняющие причину решения, часто со ссылкой на спеку.
  Новый неочевидный выбор сопровождать таким же комментарием.
- **Структура пакета:** `src/`, `test/*.test.js`, `test/helpers/`, `test/fixtures/` (бинарные
  аудио-фикстуры есть у `metadata-local-fs`), `package.json`, `tsconfig.json`, `tsconfig.build.json`.

## 5. Тестирование

**Что есть:** у каждого пакета, кроме `ts-consumer-fixture` и обоих `apps/*`, свой набор
`test/*.test.js` на `node:test` + `node:assert/strict`, без фреймворков и mock-библиотек.
- `packages/core/test/` — по файлу на модуль (`CorePlayer`, `Queue`, `Resolver`, `PluginRegistry`,
  `EventEmitter`), `index.test.js` (публичные экспорты), моки в `helpers/mockPlugins.js`,
  `helpers/fixtures.js` (`makeTrack`).
- Плагины — `index.test.js` (поведение) + conformance через `@unitrack/conformance-kit`.
- `conformance-kit` проверяет сам себя на корректных и намеренно сломанных моках из core.
- `apps/electron-demo`, `apps/web-demo` — без автотестов, проверяются вручную.

**Что добавлять:**
- Изменение поведения → тест, который падает без изменения и проходит с ним, в пакете, где
  живёт поведение.
- Баг-фикс → регрессионный тест (в истории `fix:`-коммиты в пакетах с тестами, как правило,
  меняют и тесты; исключение — `electron-demo`, где автотестов нет).
- Новый плагин → поведенческие тесты + conformance-тест.
- Изменение контракта → тесты `PluginRegistry`, conformance-kit, обновление моков
  (`mockPlugins.js`), conformance-тестов всех плагинов и `ts-consumer-fixture`.
- Тест-файлы кладутся строго в `test/` с суффиксом `.test.js`: скрипт запускает
  `node --test test/*.test.js` (без рекурсии), вложенные каталоги не подхватываются.

**Запуск:**
```bash
npm install                              # один раз; в CI: ELECTRON_SKIP_BINARY_DOWNLOAD=1 npm ci
npm test                                 # все workspace
npm test -w @unitrack/core               # один пакет
cd packages/core && node --test test/Queue.test.js   # один файл
```

## 6. Проверки

Lint/format-команд в проекте нет. Фактические команды (корень):

| Команда | Что делает |
| --- | --- |
| `npm test` | `node --test` во всех workspace (`--if-present`) |
| `npm run build:types` | генерирует `.d.ts` в `dist/` каждого пакета |
| `npm run typecheck` | `tsc -p tsconfig.json` во всех workspace (`--checkJs --strict`) |
| `npm start -w @unitrack/web-demo` | dev-сервер `http://localhost:8080` (ручная проверка) |
| `npm start -w @unitrack/electron-demo` | окно Electron (ручная проверка звука) |

**Обязательно после изменения кода:** то же, что в CI, в том же порядке:
`npm test` → `npm run build:types` → `npm run typecheck`. Typecheck потребителей резолвит типы
`@unitrack/*` через `exports.types` → `dist/*.d.ts`, поэтому без свежего `build:types`
typecheck зависимых пакетов либо падает, либо проверяет устаревшие типы.

**Допустимый минимум для локальной итерации:** `npm test -w <пакет>` и
`npm run build:types && npm run typecheck` (типы дешёвые, запускать по всему репо). Перед
отчётом — полный набор.

**Ситуативно:**
- Изменения в `apps/web-demo` или в `any`/`web`-плагинах, которые он использует — ручной прогон
  web-demo, если есть возможность; иначе указать в отчёте, что не проверялось.
- Изменения в `apps/electron-demo`, `engine-web-audio`, `metadata-local-fs` (main-процесс) —
  ручная проверка в Electron; агент обычно не может её выполнить — сообщить об этом.
- Изменения `types.js` — дополнительно убедиться, что `ts-consumer-fixture` проходит typecheck
  (входит в `npm run typecheck`).
- Добавлен/удалён workspace-пакет — `npm install`, проверить изменения `package-lock.json`.

## 7. Документация и спецификации

**Обновлять:**
- `README.md` — при добавлении/удалении пакета (таблица Packages) или изменении команд.
- `CONTEXT.md` — при появлении или изменении доменного термина.
- JSDoc в `types.js` — вместе с любым изменением контракта.
- `docs/ai/ARCHITECTURE.md` — только если задача меняет архитектуру (слои, границы, точки
  расширения); иначе не трогать.

**Спеки и планы (`docs/superpowers/specs/`, `docs/superpowers/plans/`):**
- Новая функциональность/контракт → новая спека `YYYY-MM-DD-<topic>-design.md` (разделы как у
  существующих: Purpose, Scope, решения, Testing, Non-goals) и план `YYYY-MM-DD-<topic>.md`.
  Создавать, только если задача это включает или пользователь согласился.
- Существующие спеки — исторические записи решений. Не переписывать их задним числом;
  расхождение кода и спеки — сообщить (README: «worth fixing explicitly rather than silently»).

**Не менять:** документацию, не связанную с задачей; спеки ради «синхронизации» с кодом без
явного запроса; `skills-lock.json`.

## 8. Работа с неопределённостью

Агент **не должен**:
- молча выбирать один вариант, если варианты существенно различаются по поведению, контракту
  или архитектуре;
- исправлять противоречия между документацией (README, спеки, ARCHITECTURE.md) и кодом без
  явной задачи — только фиксировать их;
- придумывать требования, которых нет в задаче, спеке или коде;
- расширять контракт «на будущее».

Для существенного решения сообщить в формате:
```
Обнаружено: <факт, с файлом/строкой>
Варианты:   A) … B) …
Предлагаю:  <вариант>
Почему:     <основание из кода/спеки/задачи>
```
и дождаться ответа, если решение необратимо или затрагивает публичный контракт.

Известные расхождения, которые нельзя «чинить» попутно (перечень на момент написания):
- спека v0.4 требует проверку непустого `id` и `initialize`/`dispose` в `PluginRegistry`,
  код этого не делает;
- `conformance-kit` описан как запускаемый в браузере, но импортирует `node:assert/strict`;
- README: `Node.js >= 18`; `metadata-local-fs`: `engines.node >= 22`;
- README требует Conventional Commits, в истории встречаются сообщения без префикса
  (`Add … design spec`, `Update package-lock.json …`);
- спека v0.4: «only changed packages receive SemVer bumps», но `@unitrack/core` остаётся `0.2.0`
  при `CONTRACT_VERSION = '0.4.0'` — правило выбора версии пакета не определено;
- `apps/electron-demo/preload.mjs` логирует `track.sources[0]?.sourceId` — поле из старого контракта.

## 9. Финальный отчёт

Компактно, для обычной задачи — несколько строк на раздел:

```
Summary:      что изменено и зачем (1–3 предложения)
Files:        список изменённых/созданных файлов
Verification: команды и результат (npm test — pass, N tests; typecheck — pass);
              что не запускалось и почему
Notes/Risks:  неоднозначности, принятые допущения, расхождения с документацией,
              что требует ручной проверки (Electron/звук)
```

Коммиты (если задача их включает) — Conventional Commits со скоупом-пакетом, как в истории:
`feat(engine-audio-queue): …`, `fix(source-subsonic): …`, `docs: …`, `chore: …`, `ci: …`.
