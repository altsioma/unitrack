# @unitrack/engine-audio-queue — First queueAuthority: 'engine' Implementation — Design Spec

Date: 2026-08-18

## Problem Statement

The v0.2.0 contract (see `2026-08-18-core-contract-v0.2-design.md`) added `queueAuthority: 'engine'` and the `setPlaybackPlan()`/`'trackChanged'` plumbing to `CorePlayer`, but no plugin package in this repo actually declared `queueAuthority: 'engine'` — the mechanism shipped with only mock-engine test coverage. Two things follow from that:

1. There is no real, usable engine a host can register to get any benefit from the lookahead-plan mechanism at all.
2. The mechanism itself was unverified against a real `<audio>` element's actual event timing (`canplay`, `ended`, `error`), and — as it turned out while building this — had two real gaps that only a genuine engine implementation surfaced: `CorePlayer` never listens for `'ended'` on an engine-owned engine at all (so an engine-owned engine that genuinely runs out of plan has no way to tell `CorePlayer` playback needs to advance), and the lookahead-plan builder (`#resolveLookaheadPlan`) ignores repeat mode entirely, meaning `repeat: 'one'` would cause an engine-owned engine to auto-advance into the actual next queue track instead of replaying the current one.

This package is the first real `queueAuthority: 'engine'` engine, chosen specifically to exercise (and, along the way, fix) that plumbing — not because iOS/AVQueuePlayer-level background playback is achievable from this repo today (there is no native host project here; see the v0.2.0 spec's Out of Scope and this document's Out of Scope below).

## User Stories

1. As a host wiring up `@unitrack/core` in a browser or Electron environment, I want a playback engine that reduces the JS work required at every track boundary, so that track-to-track transitions are less exposed to a throttled or momentarily-busy JS thread than a full `load()`/`canplay`/`play()` cycle per track.
2. As the maintainer who shipped the `queueAuthority: 'engine'` plumbing without a real consumer, I want an actual engine built against it, so that gaps only a real implementation would surface (see Problem Statement) get found and fixed while the contract is still young, rather than by the next person who tries to build one.
3. As a user with repeat-one enabled, I want that to keep working correctly even with an engine-owned playback engine, rather than the engine silently ignoring repeat mode and skipping ahead.

## Solution

### `packages/engine-audio-queue` (new package)

`createAudioQueuePlaybackEngine({ AudioConstructor })` returns a `PlaybackEngine` that owns two `HTMLAudioElement`s ("slots") instead of one. Whichever slot is currently audible is the "active" slot; the other is kept pre-loaded with whatever `setPlaybackPlan()` says comes next. When the active slot's `'ended'` fires and the other slot is already loaded and ready, starting the next track is a plain `.play()` call on an element that has already buffered — no `load()`, no waiting on a fresh `'canplay'`. The two slots swap roles (active ↔ inactive) on every hand-off; the freed slot is reset and re-armed with whatever the plan now says comes after the new current track.

`capabilities: { gapless: true, backgroundPlayback: false, queueAuthority: 'engine' }`. `gapless: true` reflects that a hand-off between two already-buffered elements has no per-track network/decode latency in the JS thread's way — not that it is sample-accurate. `backgroundPlayback` stays `false` deliberately: this engine narrows, but does not close, the JS-thread dependency at a track boundary. The active slot's `'ended'` event, and this engine's own listener for it, still have to run on this page's JS thread to trigger the hand-off — if the JS thread is fully suspended (not just throttled) at the exact moment a track ends, no amount of pre-buffering here helps. Fully closing that gap needs a native/OS-level queue (a real host integration, e.g. wrapping `AVQueuePlayer` on iOS), which this repository has no host project for yet. See Out of Scope.

`setPlaybackPlan(plan)`: loads `plan[0]` into the active slot if it isn't already there and ready (so a lookahead-only refresh — same current item, different tail — doesn't reload the audible track), then pre-buffers `plan[1]` (if present) into the inactive slot. Does not itself start playback; `CorePlayer` always follows it with `play()`, matching the existing `load()`+`play()` pattern for core-owned engines.

On the active slot's `'ended'`: if the inactive slot is loaded with `plan[1]`'s `queueItemId` and ready, the engine swaps slot roles, calls `.play()` on the newly-active (already-buffered) slot, and emits `'trackChanged'` with the new `queueItemId` — then resets the freed slot and tries to pre-buffer whatever the plan now says comes next. If nothing is pre-buffered and ready (a one-entry plan, a still-in-flight pre-buffer, or a pre-buffer that failed to load), it emits `'ended'` instead — the same signal a core-owned engine sends after every single track.

`load(resolved)` and `canPlay(resolved)` are implemented for `PlaybackEngine` contract completeness (both are required, non-optional contract members) even though `CorePlayer` never calls `load()` on a `queueAuthority: 'engine'` engine in practice — `load()` loads a single `ResolvedSource` directly into the active slot, bypassing plan tracking. `setVolume`/`getVolume` apply to both slots at once (so a hand-off doesn't cause an audible volume jump) and read from the active slot, respectively. `progress`/`error`/timeupdate/`waiting`/`playing` listeners are attached to each slot's element once, at slot-creation time, and check `slot === activeSlot` before forwarding — since `on()` is only ever called once per event by `CorePlayer#bindEngine`, per-slot forwarding has to happen internally rather than by re-registering listeners on every hand-off.

### `packages/core/src/CorePlayer.js` (two contract-gap fixes surfaced by building this)

**Fix 1 — `#bindEngine` now always binds `'ended'`, in addition to `'trackChanged'` for engine-owned engines.** Previously, an engine-owned engine's `'ended'` was never listened to at all (`#bindEngine`'s `if/else` only ever bound one or the other). Since this engine's lookahead plan is kept topped up as it's consumed (via the existing queue `'changed'` → `#refreshLookaheadPlan` cascade that already fires whenever `#reconcileEngineOwnedTrackChange` moves the queue pointer), an engine-owned engine's `'ended'` now only fires once it has genuinely run out of everything `#resolveLookaheadPlan` could resolve — at which point `#advanceOnEnded`'s existing repeat/shuffle-aware `queue.moveNext()` call is exactly the right thing to run, the same as for a core-owned engine. An engine-owned engine does not need, and must not build, a second "what's next" implementation of its own.

**Fix 2 — `#resolveLookaheadPlan` now special-cases `repeat: 'one'`.** Previously it built the plan by walking `queue.getItems()` in linear order regardless of repeat mode — meaning under `repeat: 'one'`, an engine-owned engine's next-slot would get pre-buffered with the *actual* next queue track (since the plan builder has no other input to draw from), and the engine would auto-advance straight into it on `'ended'`, silently bypassing repeat-one entirely except in the one edge case where the current track happens to be the last item in the queue. The fix pads the plan window with repeated copies of the current entry when `repeat: 'one'` is active, so an engine-owned engine's own internal auto-advance naturally replays the current track without ever needing to know repeat mode exists.

`repeat: 'all'`'s wrap-around, and shuffle order, remain documented known limitations of `#resolveLookaheadPlan` (unchanged from v0.2.0) — see Implementation Decisions below for why those two were not also fixed here.

## Implementation Decisions (need your sign-off)

1. **`backgroundPlayback: false`, not `true`, despite this being the engine built to address the WKWebView-suspension motivation from the v0.2.0 spec.** Alternative: declare `true`, since it is a meaningful improvement over a core-owned engine. Recommend: `false`, and say so explicitly in the code's doc comment. Declaring `true` would be a specific, checkable claim ("this engine keeps playing across a suspended JS thread") that chained `<audio>` elements alone cannot actually deliver — the hand-off still runs in this page's JS. Overclaiming a capability that a host might specifically filter/select engines by is worse than being honest that this is a JS-thread-dependency-narrowing optimization, not a background-playback solution.

2. **Fixing the `'ended'`-not-bound gap and the `repeat: 'one'` gap in `CorePlayer`, but not the `repeat: 'all'` wrap-around or the shuffle-order gap, in the same change.** Alternative: fix all four gaps together, or fix none and just document all four as known limitations of the mechanism this engine exercises. Recommend: fix the two that are outright *incorrect* behavior (silently hanging at end-of-queue; silently ignoring repeat-one and playing the wrong track) and leave the two that are merely *suboptimal-but-correct* behavior (a full reload instead of a gapless hand-off at a repeat-all wrap boundary; the lookahead window not respecting shuffle order) as documented limitations, consistent with how the v0.2.0 work already treated the shuffle-order gap. This engine's own tests do not exercise `repeat: 'all'` or shuffle for exactly that reason.

3. **Two slots, not a variable-size pool matching the full lookahead window (currently 3 entries).** Alternative: maintain up to `DEFAULT_LOOKAHEAD_WINDOW` pre-loaded `<audio>` elements so several hops ahead are all instantly ready. Recommend: two slots (current + one pre-buffered ahead) for this first implementation. The gapless benefit is entirely about the *next* hand-off being ready — pre-buffering further ahead than that adds real elements/network/decode cost for tracks that may never be reached (the user could skip, or the queue could change) without improving the very next transition, which is the one that actually matters for the WKWebView-suspension scenario. Revisit only if a real use case needs multi-hop pre-buffering.

4. **`setVolume` applies to both slots unconditionally, including the one that is not currently playing.** Alternative: only set volume on the active slot, and sync the inactive slot's volume right before a hand-off. Recommend: apply to both immediately — it's a single extra assignment per call, and it removes any chance of a hand-off producing an audible volume jump because the inactive slot's volume happened to be stale from before the last `setVolume()` call.

## Testing Decisions

1. `packages/engine-audio-queue/test/index.test.js`: capabilities shape; `initialize`/`dispose` (including that `dispose()` pauses both slots); `setPlaybackPlan()` loading the first entry into the active slot and pre-buffering the second into the other, without starting playback; a single-entry plan leaving the other slot untouched; `play()` starting the active slot; a ready pre-buffered next entry handing off via a plain `play()` on `'ended'` with no reload; `'ended'` (not `'trackChanged'`) reported when nothing is pre-buffered and ready; `'ended'` (not a hand-off) reported when the active slot ends while the pre-buffer is still genuinely in flight; the freed slot being reset and re-armed with the plan's new next entry after a hand-off; `progress`/`error` events only forwarded from the currently active slot; a media error during a `load()` in flight not double-reporting as a steady-state `'error'`; a same-current-item `setPlaybackPlan()` call (simulating a lookahead-only refresh) not reloading the active slot; `canPlay()`'s format/mime lookup; `setVolume`/`getVolume` applying to and reading from the right slot(s), including clamping and non-finite-input handling; `pause`/`stop`/`seek` delegating to the active slot; `getState()`; standalone `load()`.
2. `packages/engine-audio-queue/test/helpers/domStubs.js`: a from-scratch fake `<audio>` element (mirroring `@unitrack/engine-web-audio`'s test stub), but with a constructor factory that returns a *fresh* instance on every `new AudioConstructor()` call and records all instances on `.instances` — needed because this engine constructs two independent elements, unlike `engine-web-audio`'s single-instance stub.
3. `packages/core/test/CorePlayer.test.js`: the existing `'a queueAuthority: "engine" engine's "ended" event is ignored...'` test is replaced — it asserted the exact behavior Fix 1 above removes — with a test asserting a genuine `'ended'` from an engine-owned engine now advances the queue via the normal `queue.moveNext()` path, same as a core-owned engine's `'ended'` would. New test: `repeat: 'one'` pads the lookahead plan handed to an engine-owned engine with the current item instead of the actual next queue item.
4. Final counts after this change: 20/20 new `@unitrack/engine-audio-queue` tests, 123/123 `@unitrack/core` tests (was 122 — net +1 after replacing one test and adding two, minus the one test that became redundant and was removed), `tsc --checkJs` clean across all 9 workspace packages (8 existing + this new one).

## Out of Scope

- **Any actual background-playback resilience.** As stated in Implementation Decision 1, this engine explicitly does not solve the WKWebView-suspension problem — it narrows the JS-thread dependency at a track boundary, nothing more. A genuine fix needs a native/OS-level queue, which needs a native host project this repository does not have.
- **A `navigator.mediaSession`-integrated engine** (OS-level play/pause/next-track controls from a lock screen or notification). A real, useful piece of future work, but a distinct capability from `queueAuthority` — it's about OS control surfaces, not queue ownership — and was considered and set aside in favor of this option when scoping the first `queueAuthority: 'engine'` implementation (see the earlier platform-choice discussion).
- **Wiring `@unitrack/engine-audio-queue` into `apps/electron-demo`.** The demo currently registers `@unitrack/engine-web-audio` only. Swapping or adding this engine to the demo host is a natural follow-up but a separate, host-wiring-focused change, not part of building the engine itself.
- **The `repeat: 'all'` wrap-around and shuffle-order gaps in `#resolveLookaheadPlan`.** See Implementation Decision 2 — both remain documented known limitations, unchanged from the v0.2.0 work, deliberately not fixed alongside the two gaps this change does fix.
- **A configurable/multi-hop pre-buffer window.** See Implementation Decision 3 — this implementation always pre-buffers exactly one track ahead, via exactly two slots.
