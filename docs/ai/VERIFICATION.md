# Самопроверка результата — инструкция для AI-агента

Выполняется перед завершением любой задачи, изменяющей файлы проекта. Документ задаёт
порядок проверки; сами правила — в [`ARCHITECTURE.md`](ARCHITECTURE.md),
[`DEVELOPMENT.md`](DEVELOPMENT.md) и [`CLAUDE.md`](../../CLAUDE.md), примеры применения —
в [`TASKS.md`](TASKS.md).

## 1. Цель проверки

Перед завершением задачи убедиться, что:
- реализация соответствует исходному требованию — не больше и не меньше;
- архитектурные границы соблюдены;
- изменён только необходимый scope;
- публичные контракты не изменены без необходимости;
- необходимые тесты добавлены или обновлены;
- обязательные проверки выполнены;
- несвязанных изменений нет;
- открытые вопросы и ограничения явно указаны.

## 2. Порядок проверки изменений

После реализации, по шагам:
1. **Diff.** Просмотреть полный список изменённых, созданных и удалённых файлов
   (`git status`, `git diff`) — включая `package-lock.json`, `dist/` не должен попадать в изменения
   (он gitignored).
2. **Соответствие задаче.** Для каждого изменения ответить: какое требование задачи оно
   выполняет. Изменение без ответа — кандидат на откат (раздел 6).
3. **Несвязанные изменения.** Нет переформатирования, переименований, «попутных» правок
   (`DEVELOPMENT.md` §2).
4. **Архитектура** — раздел 5.
5. **Публичные API/контракты**, если затронуты: экспорты `src/index.js`, `@unitrack/core/types`,
   публичные методы и события `CorePlayer`, формы типов в `types.js`. Проверить, что изменение
   было согласовано, и найти всех производителей и потребителей (`TASKS.md`, сценарий 3).
6. **Тесты** — раздел 4.
7. **Документация/спеки** — обновлены, только если изменение этого требует (`DEVELOPMENT.md` §7);
   существующие спеки не переписаны.
8. **Риски и неоднозначности** — раздел 7; зафиксировать для финального отчёта.

## 3. Автоматические проверки

Команды проекта (`DEVELOPMENT.md` §6), выполняются из корня репозитория:

```bash
npm test
npm run build:types
npm run typecheck
```

- В процессе разработки допустимо запускать релевантное подмножество (например,
  `npm test -w <пакет>`) — по `DEVELOPMENT.md` §5–6.
- Перед завершением изменения кода — итоговый набор из `DEVELOPMENT.md` §6, в указанном
  порядке (`build:types` до `typecheck`).
- Если проверку выполнить невозможно (нет зависимостей, нет сети, нужна ручная проверка
  Electron/звука) — это не «пройдено»: указать в Verification, что не выполнено и почему.
- Упавшая проверка — не повод завершать задачу: исправить причину или сообщить о ней.

## 4. Проверка тестов

- **Новое поведение** имеет тест в пакете, где это поведение живёт (`DEVELOPMENT.md` §5,
  «Что добавлять»).
- **Изменённое поведение** имеет регрессионный тест; старое поведение, которое должно сохраниться,
  тоже покрыто.
- **Plugin / source provider / playback engine:** conformance-тест через
  `@unitrack/conformance-kit` есть и проходит (`DEVELOPMENT.md` §3).
- **Публичный контракт:** проверены все производители и потребители — плагины, моки
  `packages/core/test/helpers/mockPlugins.js`, `conformance-kit`, `ts-consumer-fixture`, хосты
  (`DEVELOPMENT.md` §5).
- Новые тест-файлы лежат в `test/` и названы `*.test.js` — иначе скрипт их не запустит.
- Существующие тесты **не удалены и не ослаблены** ради прохождения. Если тест противоречит
  задаче — это вопрос к пользователю (`DEVELOPMENT.md` §2).

## 5. Проверка архитектуры

По `ARCHITECTURE.md` §5 и §6:
- **Зависимости между пакетами:** новые `import` и записи в `package.json` допустимы по
  направлению зависимостей; плагины не импортируют друг друга.
- **Слой / уровень:** код лежит там, где ему место — `core`, `shared`, `plugins/{any,web,desktop}`,
  `apps/<host>`; используемые API соответствуют уровню пакета.
- **Границы плагинов:** провайдер не знает об очереди и движках, движок не принимает решений
  о политике очереди; `token.token` и `headers` не попадают в логи, события и ошибки.
- **Ядро:** в `packages/core` не появилось зависимостей от плагинов, shared-пакетов, хостов,
  Node API или DOM; публичные команды `CorePlayer` идут через `#enqueue`; `QueueManager` не
  стал публичным.
- **Точки расширения:** новая функциональность добавлена через существующие контракты и места
  из `ARCHITECTURE.md` §6, а не в обход них.

## 6. Проверка scope

- Изменены только файлы, необходимые для задачи.
- Нет несвязанных рефакторингов.
- Случайно обнаруженные проблемы, не относящиеся к задаче (в том числе известные расхождения
  из `DEVELOPMENT.md` §8), **не исправлены** — только упомянуты в отчёте.
- Документация, версии пакетов, `CONTRACT_VERSION` и `package-lock.json` изменены только если
  этого действительно требует изменение (например, lock-файл — при добавлении/удалении
  workspace-пакета).

## 7. Проверка неоднозначностей

Перед завершением проверить: не принято ли самостоятельно решение там, где инструкции
требуют спросить пользователя (`DEVELOPMENT.md` §8) — выбор между существенно разными вариантами,
изменение контракта, версия контракта/пакетов, необходимость спеки, неясные граничные случаи.

Если вопросы остаются:
- не скрывать их;
- явно перечислить в Risks / Open Questions;
- не выдавать предположение за принятое решение — помечать его как допущение.

Для архитектурных и контрактных решений — формат «Обнаружено / Варианты / Предлагаю / Почему»
из `DEVELOPMENT.md` §8.

## 8. Definition of Done

- [ ] Требование задачи выполнено
- [ ] Scope изменений проверен
- [ ] Архитектурные границы соблюдены
- [ ] Публичные контракты проверены
- [ ] Тесты добавлены/обновлены при необходимости
- [ ] Обязательные проверки выполнены
- [ ] Документация/spec обновлена при необходимости
- [ ] Несвязанных изменений нет
- [ ] Риски и открытые вопросы указаны

## 9. Финальный отчёт

Формат — из `CLAUDE.md`: **Summary / Changes / Verification / Risks / Open Questions**.

В **Verification** перечислять фактически выполненные проверки и их результат, например:
```
npm test            — pass (все workspace)
npm run build:types — pass
npm run typecheck   — pass
web-demo вручную    — не выполнялось: нет доступа к S3
```
Не писать «всё проверено» без списка команд и результатов.
